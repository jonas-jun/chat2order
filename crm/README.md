# crm — 구매자별 주문 집계

기간을 지정해 **구매자별 주문 횟수·상품·수량**을 엑셀로 뽑는 일회성 분석 도구.
보상 대상(단골) 선정용이며 서비스 런타임(`app.py`)과는 분리되어 있다.

```
crm/
├── customer_summary.py         # 집계 로직 (순수 함수, DataFrame in → out)
├── export_customer_summary.py  # CLI: Supabase 조회 + 엑셀 쓰기
└── output/                     # 산출 xlsx (gitignore. 개인정보 포함)
```

테스트: `tests/test_customer_summary.py`

## 실행

```bash
export SUPABASE_URL="https://<project-ref>.supabase.co"
export SUPABASE_KEY="<Supabase Project Settings → API 의 secret / service_role 키>"

python -m crm.export_customer_summary \
    --start 2026-06-01 --end 2026-09-01 \
    --user-id uiwe2156@gmail.com \
    --strip-chat-prefix "O이지픽_"
```

- `--end` 는 **제외 경계**다. 8월까지 포함하려면 `2026-09-01`.
- `--user-id` 를 생략하면, 기간 내에 계정이 둘 이상 섞여 있을 때 계정별 주문 수를 보여주고
  중단한다. 같은 대화 파일을 개발 계정으로 재추출한 이력이 있어 섞으면 이중 계상된다.
  의도적으로 합치려면 `--all-users`.
- `anon` 키는 RLS 에 막혀 0건이 나올 수 있다. 0건이면 에러로 중단한다.
- 그 외 옵션: `--time-basis {created,live}`, `--keep-file-suffix`, `--strip-emoji`,
  `--strip-chat-prefix`, `--top N`, `--output`.

## 출력 시트

| 시트 | 내용 |
|---|---|
| `구매자요약` | **요청 기준**: `채팅명 + 주문자명` 단위. 주문횟수·총수량·상품종류수·첫/마지막 주문일·대표전화번호·`주문상품요약`(`상품(옵션) x수량, …`) |
| `구매자별상품` | 구매자 × 상품/옵션 단위 수량 |
| `채팅명요약` | 채팅명만으로 묶은 요약 |
| `전화번호요약` | 전화번호로 묶은 요약. 이름 기준 집계의 교차 검증용 |
| `주문내역` | 중복 제거 후 원본 row (재집계·검증용) |
| `제외_미해결항목` | resolver 가 상품을 확정하지 못해 **집계에 들어가지 않은** 항목 |
| `집계기준` | 실행 파라미터와 진단 수치 |

## 집계 정의

- **주문 1건** = `(라이브 일자, 채팅명)`. 대화 파일 1개가 주문 1건이므로(`ui/tab_order.py`)
  같은 날 같은 채팅명은 1건으로 센다.
- **라이브 일자** = 기본 `extracted_orders.created_at`(추출 시각)의 날짜.
  `--time-basis live` 로 `extraction_jobs.live_start_time` 을 쓸 수 있으나, 이 컬럼에는 UI
  기본값이 그대로 남은 job 이 있어(추출 월과 다른 월을 가리키는 job 이 실제로 존재) 기본값이
  아니다. `live` 를 쓰면 그런 job 은 추출 일자로 대체한다.
- **총수량** = 중복 제거 후 `volume` 합.

## 데이터에서 확인된 함정 (코드가 처리하는 것)

1. **`order_number` 는 전역 유일하지 않다.** `f"{추출일}{순번:03d}"` 이고 순번이 job 마다
   1로 리셋된다(`ui/tab_order.py`). 주문 단위 키로 쓰면 다른 날 주문이 같은 건으로 합쳐진다.
2. **같은 대화 파일을 여러 번 추출한 job 이 있다.** 같은 날 95 row job 3개, 146 row job 4개 등.
   그대로 두면 수량이 배로 부풀려지므로 `(라이브일자, 채팅명)` 마다 **job 하나의 주문 내역만**
   남긴다(row 가 가장 많은 = 가장 완전한 job, 동수면 나중에 추출한 job).
   row 내용을 비교해 지우는 방식은 두 방향으로 틀린다 — 한 job 안의 동일 상품 여러 row 는
   실제 주문 수량이라 지우면 수량이 깎이고(`새틴바지` x1 이 3 row), 재추출 사이에
   `order_name`·`phone_number` 가 엇갈리면(한 번은 이름을 잡고 한 번은 못 잡음) 중복이
   걸러지지 않는다. 주문 건수는 distinct 기준이라 영향받지 않는다.
3. **저장된 시각은 KST 벽시계에 `+00:00` 라벨이 붙은 값이다.** `database._rows_from` 이
   `datetime.now()`(컨테이너 TZ=Asia/Seoul)를 naive 문자열로 넣고 컬럼이 `timestamptz` 여서
   생긴 결과다. tz 변환하면 9시간 밀리므로 UTC 로 읽고 tz 를 떼어 KST 벽시계를 복원한다.
   (`settings.kst_month_range` 가 `+09:00` 경계를 쓰는 `extract_call_logs.called_at` 과 다르다 —
   그쪽은 DB 기본값 `now()` 로 채워지는 진짜 UTC 값이다.)
4. **PostgREST 응답 상한 1000 row.** `.range()` 로 페이지네이션한다.
5. **동일인이 여러 표기로 쪼개진다.** 다음만 자동으로 합친다.
   - 파일 중복 다운로드로 붙는 `" (1)"`, `" (2)"` 접미 (`--keep-file-suffix` 로 해제)
   - 채팅명 끝의 `_<주문자명>` — 잘라내는 토큰이 그 row 자신의 주문자명과 같을 때만
   - 주문자명이 빈 주문 — 주문자명이 **유일하게** 확정될 때만 채운다. 같은 날 같은 채팅명
     범위를 먼저 보고, 남은 것은 채팅명 전체 범위로 본다
   - 주문자명의 공백 (`"나 소희"` = `"나소희"`)

## 남는 한계 (사람이 확인해야 하는 것)

- **동명이인이 한 행으로 합쳐진다.** `전화번호종류수` 컬럼이 2 이상이면 서로 다른 사람이
  섞였을 수 있다. 보상 대상을 확정하기 전에 `주문내역` 시트에서 해당 구매자를 확인할 것.
- **주문자명을 못 채운 구매자가 남는다.** `주문자명 = (미상)`. 채팅명만으로 식별해야 한다.
- **전화번호가 없는 주문이 약 25% 있다.** 그래서 `전화번호요약` 의 주문횟수는 하한선이며,
  전체 순위 대신 교차 검증용으로만 쓴다.
- **`제외_미해결항목` 은 집계에 없다.** resolver 가 상품을 확정하지 못한 주문이라 수량이
  그만큼 과소 집계된다.
